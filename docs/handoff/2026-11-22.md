## What changed

**DLP suppressions are now visible where the decision matters.** An approved
suppression used to exist as a record with no effect on any screen. It is now:

- resolved per finding by `DlpSuppressionResolver`, bound as a scoped singleton
  so the finding table and the quality page share one in-force query per request;
- shown as an **Accepted by** badge in the finding queue (reference `DS-0001`);
- creatable from a finding with a **Suppress** action, seeded from the finding's
  policy, identifier type and match label, and still requiring a second approver;
- counted on the DLP quality page as **Accepted**, overall and per identifier
  type. It does not change the false-positive rate: a suppression is an
  acceptance, not a review outcome.

No schema change, no new table. The resolver matches policy, then the optional
identifier type and match label, reusing `DlpSuppression::appliesTo()`.

## Addendum: evidence stream operations screen

`Admin → System → Evidence streams` now shows each stream's client, name, active
state, last accepted time, last cursor, accepted and rejected counts and the last
rejection reason. Admin-only, because the row carries the signing secret even
though the screen never renders it. An admin can disable a stream (the producer
gets `403` immediately) and enable it again; creating and rotating a secret stay
on the CLI per ADR 0054.

`EvidenceStreamPolicy` is mapped explicitly in `AppServiceProvider`: the
project's `guessPolicyNamesUsing` returns `AppPolicy` for unmapped models, so a
new policy is inert until it is added there. That is worth remembering for the
next model with its own policy.

Tests: `tests/Feature/Evidence/EvidenceStreamUiTest.php` (3) — counters rendered
and secret absent, editor/viewer forbidden, disable and enable through the table
action. Tagged `v0.1.0-alpha-8`; stack rebuilt, doctor strict green.

## Still open, stated plainly

1. **Evidence streams are CLI-only.** There is no screen for the counters, last
   rejection reason or disabling a stream; an operator has to query MySQL.
2. **The assistant has no producer.** ADR 0055 is implemented and tested, but no
   question calls the proposal service, so the queue stays empty until one is
   wired as a reviewed use case.
3. **The immutable audit-log pillar is not started.** `activity_log` is still an
   editable table; applying the evidence-ledger pattern is the next large
   architectural change.
4. **Streaming is disabled** until an operator enables it and creates a stream.
5. The two assistant operations are the entire write surface; adding a third is a
   reviewed catalogue change, not a prompt edit.
